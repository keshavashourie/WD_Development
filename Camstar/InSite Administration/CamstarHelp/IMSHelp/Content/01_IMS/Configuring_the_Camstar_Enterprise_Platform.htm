Configuring Opcenter EX MDD or Opcenter EX CR

The Configuration pane is used to specify various system parameters.

When Configuring Opcenter EX MDD or Opcenter EX CR

Prerequisites

These are prerequisites for configuring Opcenter EX MDD or Opcenter EX CR:

• You must set the Metadata database before you can specify the default security domain.
• You must set a default security domain on the Configuration pane before you can start the Application Server.
• You must specify a single sign-on method of authentication on the SSO tab.
• You must specify a REST API user name and password if you are using the REST APIs.

Database Connections

Database connections are cached in the Application Server. The connections in the connection pool are not released back to the pool as long as the server is actively using the connection. The only way to clean up connections is to stop and start the Application Servers.

Idle database connection cleanup is controlled by two fields in the InSite SiteInfo table in the SiteInfo.mdb. Information for these fields is entered in the Configuration pane:

• Enable idle connections cleanup

This check box enables logging of the connection cleanup to the event log.

• Close connections after being idle for

This field populates the LogDBConnectionCleanup value in the table. The value is in seconds and indicates the amount of time a connection must be idle before it is closed.

Note: You may want to enable logging initially so you can verify that connections are being cleaned up. You should clear this value to disable logging activity once the database is in production.

Notification Server

The Notification Server is a stand alone .NET-based service. It uses its own configuration file to establish connection to the database from which e-mail messages are polled.

Generated e-mail messages are stored in a table in the database with the SMTP Server connection information. The Notification Server polls this table for new e-mail messages to send, and then sends the messages to the SMTP Server for delivery.

The Notification Server includes a retry mechanism for messages that cannot be sent successfully. For multiple Notification Servers that are accessing the same database, a row locking mechanism is provided to ensure that the e-mail message is only processed by a single server.

E-mail notification uses the Notification Server to submit e-mails to the SMTP Server. The Configuration settings in Management Studio contain the settings for the Notification Server. You can modify the Configuration settings to change the way the Notification Server works.

Note: When setting the Sessions parameter in your Oracle database, keep in mind that the Notification Server takes approximately 100 connections against the database. Refer to "Sample Database Creation Parameters" in the Opcenter Execution Medical Device and Diagnostics System Administration Guide or the Opcenter Execution Core System Administration Guide for information on the Sessions value.

Permissions Required for a Local Account to Run the Notification Server Service

Normally, if the Notification Server account is run under a particular user, that user must be a member of the local Administrators group. However, if a non-administrative local account at your site is utilized to run the Notification Server service, then a system administrator must set these permissions:

• For the non-administrative local account, set Read/Write access to the .config files in the directory in which the applications reside.
• For the IIS user group, set Read access to the same .config files.

This is also true of the Security Server.

Application Servers in a Network Load Balancing (NLB) Cluster

If your Application Servers are in an NLB cluster and you have more than two nodes, it is a best practice to have the Notification Server running on no more than two of them. The service polls the database every second by default to search for new e-mails to send. Contention issues can occur if multiple servers poll the same table frequently. Additionally, each Notification Server instance creates approximately 100 connections against the database.

Configuring E-Mail Notification Settings for Quality Records

The topic, "Configuring WIP E-Mail," in the System Administration Guide discusses the configuration of Opcenter EX MDD or Opcenter EX CR to send maintenance and WIP message e-mails when an operator completes a transaction on a resource. This is a separate function from the quality record E-mail notification function.

Configuring License Expiration Notifications

Opcenter EX MDD and Opcenter EX CR provide the ability to automatically notify designated recipients when their license expires. You can also use Management Studio to configure settings to send e-mail notices at intervals before the license expires. There are two intervals you can set:

• Warning Period
• Critical Period

The application sends the e-mail notification once per period: once for warning and once for critical. For example, if you set the warning period to 30 days and the critical period to 15 days, you will receive a warning notice 30 days before your license expires followed by a critical notice 15 days before your license expires. You will also receive an e-mail when the license expires.

Single Sign-On

Using the single sign-on authentication approach, users can access multiple Siemens on-premise or cloud-based applications by logging into any of the applications. The single sign-on approach provides a single identity and access management solution across the full ecosystem of Siemens applications and services.

You must configure single sign-on in Management Studio to enable single sign-on.

Single sign-on is available in the desktop mode and in the mobile mode.

The log in options are:

• Default - The default log in implementation is logging in without single sign-on. You can continue using the existing log in functionality by entering your username and password.
• SAM - The Security and Access Management (SAM) authentication mechanism validates authorization as required by Siemens services for access to other Siemens services and resources. A unique access key (Webkey) is generated for all account IDs and services, and the SAM service validates the authorization as needed to access the other services.
• SAML- Authentication via SAML adapter is extended to Azure Active Directory (Azure AD).
Refer to "How to Build a SAML Application using the ID Portal (Azure AD)" for more information.
Refer to the Azure AD documentation for more information on this option.
• Windows Authentication - Authentication using your Windows credentials.
• Smart Card - Authentication using smart cards.
Note: Security and Access Management (SAM) authentication is the only single sign-on authentication method available for Siemens cloud-based services.

Cross-Origin Resource Sharing (CORS)

CORS is a mechanism defined by the Fetch API Specification that allows REST API to specify which origins are permitted to access its resources. This is essential for web security because browsers block requests from different origins by default for security reasons.

Only requests from origins you specify (for example, https://example.com) are allowed to access the API. If you try to access the API from a different origin, the request is denied due to the CORS policy. If an application from an unapproved origin attempts to access the API, it receives a CORS error response. This prevents unauthorized domains from using your API.

When you specify an origin on the CORS tab and click Save, the application updates the appsettings.json file for each REST API service (Modeling, Shopfloor, Query, and Labels). The application writes the information to the AllowedOrigins section:

"AllowedOrigins": [

"https://example.com"

]

Note: If you have manually entered information in the AllowedOrigins section of any of the appsettings.json files, it will be overwritten by any origins you specify in Management Studio.

From a web application hosted at https://example.com, a GET request to https://{server}/modeling, for example, succeeds if you have specified the origin in the allowed list (whitelist) on the CORS tab. A request from an unauthorized origin, such as https://unauthorized.com, is blocked by default according to the CORS policy.

Single Sign-On Setup Script

When SAM or SAML is selected as the SSO option in Management Studio, the SSO Setup button is displayed. Using this button you can configure single sign-on by executing an automated script that sets up all the necessary URLs for both SAM and SAML. This script ensures faster setup, reduced manual errors, consistency across environments and easier replication of configurations. The script configures all necessary URLs (e.g., Identity Provider (IdP) metadata URL, Callback URL, Logout URL etc). The script also handles certificate uploads and references.

1. On the Management Studio page, select either SAM or SAML from the Sign-in Via dropdown.
2. Select the SSO Setup button. A warning is displayed indicating that all the previously configured URLs will be overwritten. Click Yes.The Power shell terminal to update the web.config file opens.
3. On the interface you are prompted to enter the Opcenter Admin username and password. Retype the password to confirm.
4. Enter the login method SAML/SAM. Type Y to confirm.
5. Confirm the server name. By default the application selects the name of the server you are currently working on. You can either continue with the default selection and type Y, or type N and select a different server. Type Y once again to confirm.

How to Build a SAML Application using the ID Portal (Azure AD)

Follow these steps to configure a SAML application on Azure ID:

1. Create a new SAML application on the Azure AD portal using the links listed in the table below:
• To configure the SAML application using Azure AD, use the following links -
For internal Siemens users- https://wiki.siemens.com/display/en/OneAD+Wiki and navigate to the section, "How to onboard an application to Siemens Azure AD single sign-on (OIDC/SAML)"
For external users- https://learn.microsoft.com/en-us/azure/active-directory/manage-apps/add-application-portal-setup-sso
Note: This step populates the value for the External IDP Public Key field.
2. Set the SSO configuration path in the IDP agent, in the appsettings.json file. For example:
"SSOSettingFileName": "SSOConfig.json",
"SSOSettingFilePath": C:\Program Files (x86)\Camstar\InSite Administration"
3. Download the certificate (the .cert file ) from the IDP portal and save it in the folder where the IDP agent is deployed. For example: Navigate to the installation directory where Opcenter Execution Core or Opcenter Execution MDD is installed and navigate to \SSO\IdpAgent\app_data\Certificates. Create the app_data\Certificates folder if it is not present.
Note: For Azure AD download the base64 certificate. If running through script, the folder is created automatically and this step can be skipped.
4. A private key is created when user selects SAML in Management Studio that is stored in app_data/jwt folder. By default, the password is set to 'localhost'. If required, you can retrieve the cert.pfx file from app_data/jwt folder.
5. Copy the text from the IdpSaml.crt certificate, in the verify certificate section of the SAML application.
6. To reset the IIS, run command prompt in the Administrator mode and enter the command, C:\WINDOWS\system32\iisreset
7. Once all the configuration details for Management Studio have been generated and updated in the fields under SAML you can log into the application using the traditional login URL. For example https://localhost/CamstarPortal/Default.aspx
Note: The session timeout value should not exceed 100 minutes. Update "SessionExpireTime" in the appsettings file in IDP Agent and update "SessionState" in the web-config file for Opcenter EX CR and Opcenter EX MDD.

The"SessionState" value that is updated in the web-config file should also be configured in the IIS Application Pool. Navigate to IIS > Open Application Pool > Select Portal > Advance Setting > Idle Time-out and ensure that the Idle Time-out setting is configured to match the value defined for "SessionState."
Note: While creating or configuring the SAML application on IDP (for example Azure AD), use this logout URL to send the SAML response back to the application - https://<mydomain>/IDPAgent/api/v1/sso-service-provider/saml-logout-response.

Enabling Logging when using SAML

To troubleshoot SAML logs, you can enable logging for the IDP Agent and review the logs in the IDP Agent Log folder.

Enabling IDPAgent Logs

Follow the steps outlined below to enable logging for the IDP Agent:

1. Open IIS and navigate to Application Pool.
2. Go to Advanced Settings.
3. Under Application Pool Identity, change from Network Service to LocalSystem.

4. Once logging is enabled, perform an IISReset. Log in again and proceed to check the logs.
5. To access the IDP Agent log path, navigate to IIS and locate the IDPAgent Site.
6. Right-click on the IDPAgent site and select Explore.
7. Check the IDP Agent Log folder to review the logs for any errors.

How to Configure Opcenter EX MDD or Opcenter EX CR

Follow these steps to configure Opcenter EX MDD or Opcenter EX CR:

1. Click Start > Opcenter Execution MDD > Management Studio. The Management Studio window appears.

Or

Click Start > Opcenter Execution Core > Management Studio. The Management Studio window appears.

2. Expand the Configuration folder in the Sites tree and select the Configuration node. The site configuration information appears in the right pane.
3. Click the Security tab.
4. Enter the Default Domain.
5. Click the SSO tab.
6. Select the method of authentication from the options in the Sign In Via list.
7. Enter the details based on the method of SSO selected.
Note: You can add and save configuration details of all the four single sign-on authentication modes, but the option selected (Sign In Via) and saved will be the method of authentication that is applied.
8. Click the REST API tab if you are using the REST APIs.
9. Enter the UserName and Password to use with REST API. Management Studio encrypts the password you entered, and then passes the user name and encrypted password to each of the appsettings.json files when you save.
10. Click the CORS tab if you need to specify allowed origins.
11. Click in a new row in the Origin list and enter the http address of an origin you want to allow.
12. Repeat step 11 to add another origin if needed.
13. Enter optional information according to your business requirements. Refer to the field definitions tables for information on the optional fields.
14. Click Save. Management Studio displays a success message.
