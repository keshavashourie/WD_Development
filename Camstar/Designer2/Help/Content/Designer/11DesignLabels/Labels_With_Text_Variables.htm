Labels With Text Variables

In addition to static labels, you can merge data at runtime into the label using text variables. Text variables describe how to derive a value at run-time that is to be incorporated into a message string. These are used by various objects (such as WIP Messages or History Inquiries) to incorporate variables in strings.

For example, if you execute a Start transaction and it executes successfully, the following message appears:

<Containername> started at <Start step> on <date> by <user>

This completion message is actually calling StartCompletion, a label under CSICompletion. If you view this label in the Labels library, the text for this label reads as follows:

#HistInq.Container started at #HistInq.StartStep on #HistInq.Date by #HistInq.User.

The variables (preceded by the # sign) will be replaced by appropriate text, such as the container name, name of the workflow’s starting step, transaction date, and user who entered the transaction, all taken from the HistoryMainline database table.

The TextVariable CDO

The TextVariable is a named data object used to provide values that are to be resolved at runtime and then incorporated in a message string.

The TextVariable CDO has two types used by Opcenter EX MDD and Opcenter EX CR to process labels:

• ErrorMsg

Provides the values used to construct error messages

• HistInq

Provides the values taken from the HistoryMainline CDO

Each TextVariable instance includes a name and an expression among its attributes and describes how to treat the condition where the expression cannot be successfully evaluated.

The name is the value embedded in the static string prefixed by a character that identifies it as a Text Variable. For example, a TextVariable instance with the name TEMPERATURE is included in the default label:

Set temperature to #TEMPERATURE.

Maintaining and Using Text Variables

Maintaining text variables means creating instances of the Text Variable NDO in the factory model, and then creating labels that refer to the text variable instances. Using text variables means you are defining a field to call up labels that use text variables.

In this scenario, you have a Service CDO with a field called SpecialInstruction; and you want to display the message, Set the temperature to 700 on the field. You have also created the necessary definitions for the temperature value to be stored in another CDO.

How to Maintain Text Variables

Follow these steps to maintain text variables:

1. Log in to the Portal and create an instance of TextVariable, giving it a name and expression.

For example, use Temperature as a name and CDO.Field as the format for the expression. The expression includes the CDO field from which the value, the temperature 700, is retrieved.

2. Log in to Designer or the Portal and create a label called MyInstruction that will reference the text variable instance. In the label value, type the message text to include the string, #Temperature, to correspond to the text variable instance name.

Guidelines for entering text variables in default label values are:

a. Put a placeholder for the text variable to be merged with your label value at runtime.
b. For the placeholder’s format, specify the text variable instance name.

For example, the label value for MyInstruction will be something like:

Set the temperature to #Temperature.

Using text variables

Refer to “Using Labels” to use the label with the text variables. In this case, you are configuring the Service CDO to retrieve MyInstruction, the label that has the text variable Temperature, and display it on the field SpecialInstruction.

During service processing, the field gets the label value with the proper text replacing the variable.

How Variable Expressions Are Evaluated

When you define a TextVariable, you specify an expression that will be used to locate the data. The expression is a string to be evaluated at runtime to produce the value that replaces the identifier within the runtime version of the string. This data usually comes from a CDO. The CDO to use is determined prior to the retrieval of the field.

Consider the following default label value for a completion message:

#HistInq.Container started at #HistInq.StartStep on #HistInq.Date by #HistInq.User.

The expression contains placeholders for the data from TextVariable to be merged. The placeholders specify the text variable type and its name. For error messages, the format is #ErrorMsg.CDOName; in History messages the format is #HistInq.Step.

For example, in the case of the StartStep variable above, the specified built-in expression is:

Transaction::InProcessHistoryCDO.WorkflowStep.Name

By design, one of the last tasks ContainerTxn does is use the SetFieldEx function to set Transaction::InProcessHistoryCDO to the Id of the HistoryMainline CDO for that transaction (note that this process is not exposed to the user). When the CompletionMsg field is processed, the label value above is found. The system checks the Substitute Text Variables flag, and finds that it is set, so it runs through the string and finds the placeholders, including #HistInq.StartStep. It then retrieves the HistInq text variable named StartStep, evaluates the expression Transaction::InProcessHistoryCDO.WorkflowStep.Name, and replaces the placeholder with the result (the name of the step where the container was started).

What constitutes a valid expression string will vary based on the type of message referencing the text variable. Certain expressions (and therefore text variables) can be shared by all message types. For example, a text variable may be used to incorporate values for the current SessionValues. Other expressions will only apply in the context of a particular type of message. For example, a WIP Message may include a variable for the product currently running on the machine where the Move-in transaction is presenting the WIP Message.
