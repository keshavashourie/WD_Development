Parameters

Parameters are placeholders for values required by functions and CLFs at runtime. A parameter has a unique name, an input/output direction, a multiplicity, a data type, a default value, and a description, among other attributes. The set of parameter specifications for a given function or CLF defines its interface in Opcenter EX MDD or Opcenter EX CR, or communication protocol.

Defining Function Parameters

CLFs and functions access input parameters through the unique parameter name. A parameter value can be set at design time of the function or CLF, referred to as the Default Value for the parameter, or at runtime by another function or CLF. Specifying parameters can be as simple as providing a field name or as complicated as extending the parameter into a complex expression. Parameters can be defined as:

• Numeric or string constant
• FieldName
• FieldExpression
• Variable
• FieldExpression starting with a variable
• Built-in variable
• Label or LabelID designator

If you choose to use an expression to represent your parameter, refer to "Unified Expressions" for information on the correct syntax.

Parameter Data Types

If a function’s Enforce Parameter Types flag is set on the function’s General tab, you can further define the parameters according to the following four classes of parameter data type:

1. Trivial

A parameter of type class Trivial can be any of the following types: String, Boolean, Timestamp, as well as the Numeric types (Integer, Fixed, Float, Decimal)

2. Fundamental

This type class consists of the basic parameter data types. They include the Trivial data types as well as Object and Numeric.

3. Object

A reference to a CDO. If the parameter of type Object, the Object name is also specified.

4. Numeric

A parameter of type class Numeric can take any of the following types:

a. Integer: 32-Bit Integer
b. Float: Floating point number
c. Fixed: Fixed number of decimal and whole number positions. The fixed data type is used to store a fixed point number as a floating point number in the database. A floating point value is an approximation of a fixed point value. Note that a Decimal type is available and should be used to store an exact numeric value.
d. Decimal: A fixed point type, an exact numeric value as opposed to an approximate numeric type like float.
e. Any:A parameter of type class Any can be any of the other data types and type classes as well as:
• Resultset: Parameters that are recordsets. For example, parameters that are results of an advanced query.
• Parameters: Parameters that pass Name/Value pairs; for example, parameters passed to queries.

Type Multiplicity

Parameter data types are further characterized by type multiplicity. This means that you can specify if the parameter will be Scalar, or a List, or either (ListOrScalar).

Multiplicity

This attribute specifies the number of values the parameter can or must take. The choices are 0...* (zero or more, therefore an optional list), 0...1 (zero or one, therefore optional), 1...1 (one, therefore required), 1...* (one or more, therefore a required list).

Parameter and Variable Context

CLF writers can introduce variables at any time. Variable life starts when its value is set for the first time. Parameter and variable context refers to the context in which the variable resides. Depending on what scope or context a variable belongs, the lifetime of the variable is different.

Three scopes or contexts for expressing these parameter variables are:

• Transaction (Transaction::)

The Transaction context lives within the context of the service CDO and it exists throughout the life of the instance of the CDO. If you need to keep or pass data between CLFs, use transaction scope variables. Transaction contexts are created for every instance of a particular service and they are unique for each service. Once the value of the transaction scope variable is set, it remains the same unless it is changed, such as by a CLF. All transaction context variables are discarded as soon as the service to which they belong is removed.

• CLF (CLF::)

The CLF context is created only for the time while the CLF is executed. The CLF scope variables are typically used to pass interim data between executions within a CLF. If you need to keep or pass data between executions, use CLF scope variables. Avoid using variables that by their nature belong to the CLF context in the transaction context scope. CLF context variables are also used to pass parameters to CLFs. The parameters are accessible from within the CLFs through the CLF scope.

Note: CLF:: variables are created by the application server, but can be referenced by database functions. High Performance CLF parameters are prefixed with DBCLF::, and DBCLF:: variables are created by the database stored procedures. DBCLF:: variable references are used only on the database. The application server ignores the DBCLF:: prefix and passes it to the database. Refer to "Adding High Performance CLFs for information on High Performance CLFs.
• Function (Exe::)

The Function context is for Function parameters. The function parameters are accessible through the Exe scope from within the functions. The function context is created for the time while the function is executed. Functions can also introduce local contexts with variables that are accessible through the Local scope. Local context variables are currently used for error-message processing.

A CLF context is used for the parameters for Function 1 and 2. This is because the parameter values can be passed between the functions. A transaction context could have been chosen, but the value would have survived the life of the CLF and that was unnecessary. Likewise, a function context could not have passed the parameter value between the functions because the parameter no longer exists once Function 1 is executed.

Built-in Variables

Built-in variables are either set to certain values by the application server prior to CLF invocations or used by the application server to determine what the CLF has returned.

CLF::__CDOID

Type: Object Reference

Set by the application server to the current CDO prior to invoking a CLF (both CDO and field level CLFs)

Usage: Used in CLFs to refer to the current CDO (to which the CLF is attached)

Transaction::__Return

Type: Set by the user

The application server expects CLFs to return a value in this variable in response to certain CDO or Field events.

Important: The Events section of this chapter is entirely about the Transaction::__Return built-in variable. Refer to "Editing Parameter Values for a Function" for information.

Usage: Used in CLFs to return a value set by the user

Transaction::__CurrentService

Type: Object Reference

Set by the application server to the current service at the beginning of service execution or validation

The variable can be used by CLFs attached to BeforeValidate, AfterValidate, BeforeExecute, and AfterExecute.

Note: This variable is not set until the Client code calls Service.Execute. This variable is set to each SubService while executing a CompoundTxn.

Usage: Used in CLFs to refer to the current service (regardless of the CDO to which the CLF is attached)

CLF::__FieldValue

Type: Same as the field type

Set by the application server to the current field value prior to invoking a CLF for a scalar field

Usage: Used for CLFs being attached to field events of scalar fields

CLF::__Index

Type: Integer

Set by the application server to the current list field item index prior to invoking a CLF for a list field event

The following are possible values of the variable depending on the field event:

• Value = new item index for AddItem event
• Value = current item index for ChangeItem and GetItem events
• Value = current item index for RemoveItem event
Or
-1 for RemoveItem if the item is being removed by the value
• Value = source item index for MoveItem event

(CLF::__FromIndex and CLF::__ToIndex variables are also set before MoveItem)

• Value = -1 for all other list field events

Usage: (Rarely used) For CLFs being attached to field events of list fields

CLF::__ItemValue

Type: Same as the field type

Set by the application server to the current list field item value prior to invoking a CLF for a list field

Usage: (Rarely used) For CLFs being attached to field events of list fields

CLF::SessionValues

Type: Object

Allows access to the SessionValues CDO associated with the logged-in user

Set by the System

Usage: Only available and used in CVEs

Editing Parameter Values for a Function

You can only modify parameters for user-defined functions.

How to Edit Parameter Values for a Function

Follow these steps to edit parameter values for a function:

1. Open Designer.
2. Click Functions. The Function Definitions window appears.
3. Select the user function for which you want to edit parameters.
4. Click the Parameters tab.

 

5. Select the parameter you want to modify.
6. Modify the parameter according to your business requirements.
Note: The changes are made in the Function library. If you changed the value in Default Value, all CLFs using this modified function will not be affected by the modification. You must open the CLF, remove the function, and add it back.
7. Select Save from the File menu. The application saves your changes.

How to Add Function Parameters

You can add function parameters only to user-defined functions. Note that when parameter values are added to functions that have been attached to a CDO event or method, only the template version of the CLF will be affected. If you want to use the new parameters for the CLF that had previously been attached to a CDO event or method, detach the CLF from that CDO and attach the modified CLF definition.

Follow these steps to add function parameters:

1. Open Designer.
2. Click Functions. The Function Definitions window appears.
3. Select the user-defined function to which you want to add parameters.
4. Click the Parameters tab.
5. Click Add on the parameters tab. A generic parameter appears on the list with a default name.

 

6. Enter a new name in the Parameter name field.
7. Click the generic parameter on the parameter list pane to save the name. The new name replaces the generic name.
8. Select an entry for Special processing.
9. Select a Direction for the function parameter.
10. Select a value for Multiplicity.
11. Enter a Description of your function parameter.
12. Select a data type and type multiplicity from the Data Type and Type Multiplicity lists.
13. Enter a Default Value for the parameter, if appropriate.
14. Enter notes and comments in the Notes field for the new function parameter according to your business requirements.
15. Click another tab or select a different function to save.
16. Select Save from the File menu. The application saves your changes.

How to Remove Function Parameters

You can remove parameters only from user-defined functions.

Follow these steps to remove function parameters:

1. Open Designer.
2. Click Functions. The Function Definitions window appears.
3. Select the user function from which you want to remove parameters.
4. Click the Parameters tab.
5. Select the parameter to be removed.
6. Right-click on the parameter and click Remove parameter from the shortcut menu or click Remove on the Parameters tab. A confirmation dialog box prompts you to confirm the parameter removal.
7. Click Yes. The parameter is removed from the list.
8. Select Save from the File menu. The application saves your changes.

How to Modify Default Parameters in a CLF Function

When you add a new CLF to a CDO, many of the parameter values for the functions are already provided. These are referred to as the CLF default parameter values. To modify these default values, the definition of the CLF must be modified. Note that when the default parameter values are changed, only the template version of the CLF will be affected. Consequently, parameter values of a CLF and its functions already attached to an event or method will not be affected. If you want to use the modified parameter values for the CLF previously attached to an event or method, detach the CLF there and attach the modified CLF definition.

These modifications will affect only the function for the selected CLF. Refer to "Editing Parameter Values for a Function" for information on modifying the function parameters.

Follow these steps to modify default parameters in a CLF function:

1. Open Designer.
2. Click CLFs. The Logic Flow Definitionswindow opens at the Functions tab.
3. Select the CLF from the selection window. The example shows MoveIn_Execute under ServiceProcessing.
4. Select the function to be modified in the Logic flow pane. The default parameter values for the selected function appear in the Function parameters block:

The available functions appear in the Available Functions pane.

5. Modify default parameter values as desired.
6. Optionally, select the Dynamic check box to have the parameter passed as a dynamic value using look-up expressions. Leave it deselected if you want the parameter to be passed as an actual value.
Note: If the function enforces parameter types (set by a flag in the Functions window), the Dynamic check box will not be visible and Multiplicity and Data Type columns will be visible instead. Multiplicity and Data Type are read-only in this window. To change the values for these columns, you must go to the Function definition window where you can modify user-defined functions.
7. Select Save from the File menu. The application saves your changes.
