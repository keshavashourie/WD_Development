When to Create a Table

If you are creating a subclass of a CDO that already has specific table or tables (for example, you are creating a Product subclass and the Product CDO has Product and ProductBase tables), then, in general, you will not create a new table or tables. Creating a new table or tables in this case will cause ramifications to reporting (unless no reports will use these tables).

If you put a subclass in a new table, you have to always refer to it specifically. For example, you can create a MyEmployee subclass and table. You then have to create new subclasses of every shop floor transaction that you use, and this subclass must redirect (override) its employee field to the MyEmployee subclass. That is not feasible.

The only time it is feasible to put a subclass in a different table than its superclass is when you will always refer to it specifically. A good example of when you would do this is with object groups. Usually if you are making a new subclass of an object group, you will refer to it specifically. For example, you might create a CustomerGroup object group and want to put it in a specific table, instead of leaving it in the NamedObjectGroup table, since you will normally always refer to CustomerGroup specifically (for example, in a specific Customers field in the product family).

If you are creating a subclass of a CDO that does not have specific table or tables (for example, creating a subclass of NamedDataObject, RevisionedObject, UserCode or Subentity), then you must create a new table. Otherwise, there will be no database table in which to store instance data for that new subclass.
