Defining a Subentity CDO Subclass

A subentity is an object that is owned by another object. (This ownership type of relationship is usually referred to as a composition.) A subentity object belongs to one and only one parent object. Any subentities are usually expected to live and die with the parent; if the instance of a parent is deleted, instances of its subentities will also be deleted.

When Defining a Subentity CDO Subclass

A subentity design is required when a list of items is needed, where each item has multiple attributes. For example, to model a Workflow in the Opcenter EX MDD or Opcenter EX CR object model, it is required to define Step as a subentity, and mark step as a list field in the Workflow.

It is also appropriate to use a subentity instead of adding multiple individual fields to the parent object when you would like to group a set of related fields together for reuse, encapsulation, or other purposes. For example, Opcenter EX MDD or Opcenter EX CR includes a SchedulingDetail object that contains fields such as SetupTime, RunRate, and so on. This subentity definition is used in the Operation, Spec, and WorkflowStep objects.

While only one particular parent object owns any given subentity, the subentity can be referenced by other objects. For example, a workflow owns its steps, but other objects such as a container can reference a particular workflow step. To reference another object's subentity, it is usually necessary to specify the parent of the subentity as part of the reference information.

Some of the features of a subentity CDO include:

• The parent object has references to its subentities, and each subentity has a reference to its parent.
• When an instance of a parent object is deleted, all instances of its subentities are automatically deleted.
• Either Opcenter EX MDD or Opcenter EX CR includes a special class of subentity called NamedSubentity. Named subentities are useful when you need to create a subentity list field and it is appropriate to give each subentity item a name that is unique within the parent. For example, the VendorItem subentity used as list within a Vendor is a named subentity; the system requires each item to have a name that is unique within the Vendor, and the VendorItem subentity can be referenced by specifying the vendor and the name of the item.
• Any object can contain subentities. Even subentities can contain other subentities.

Workspace prefixes are automatically inserted before the name of an item when adding a new item, if a prefix has been assigned to the highest active workspace. Workspace prefixes indicate which workspace Designer is applying changes to. For example, the prefix "C200" would be associated to the workspace with a prefix set as "C200" the highest active workspace in Management Studio. It is recommended you use the prefix supplied by Designer when adding new items.

You can assign or modify workspace prefixes in Management Studio. Refer to the Opcenter Execution Medical Device and Diagnostics System Administration Guide or the Opcenter Execution Core System Administration Guide for information.

Note: The base application workspace (csi) cannot have a workspace prefix assigned to it.

Subentities of NDOs and ROs

Opcenter EX MDD and Opcenter EX CR has highly automated the process of creating subentities for NDOs and ROs. The only steps that are required are:

• Create the subentity by adding a field on the parent object.

When adding the field, choose the [Create a new subentity] datatype. You will then be given the opportunity to pick what kind of subentity to create (such as a named subentity or a subclass of some particular existing subentity).

• Specify the attributes of the subentity, such as its name, description, storage category, and table name (if necessary), and specify whether or not the subentity should be used as a list in the current parent.
• Once you have created the subentity by adding it as a field on the parent object, navigate to the new subentity by right-clicking on the subentity field and using the Position to CDO shortcut menu option.
• Add any necessary fields to the subentity.

The Designer automatically handles all other work that enables the new subentity to be updated with the appropriate maintenance service.

Results of adding a new Subentity through the automated feature:

• A new subentity is created of the type that you selected from which to inherit.
• The new subentity contains a field that links it to the parent CDO for which you created this subentity. Its field name is Parent, and its type is the name of the parent CDO.
• The parent CDO (the CDO for which you created the new subentity) has a new field containing a reference to its new subentity. The field type is the name of the new subentity.

Subentities for Containers

The Container CDO has a subentity, ContainerDetails, referenced by the Detail field. In certain cases, you might need to add fields to customize the Container CDO. You can add them to the ContainerDetails subentity. ContainerDetails is a non-list subentity. Refer to “Subentities of Other Objects” for subentity lists.

Subentities of Other Objects

If a subentity of another subentity, a subentity of a Shop Floor service, a subentity list for a container, or other sophisticated subentities are necessary, more Designer configuration will be needed. Necessary steps depend on the particular task, but might include:

• Generating the new subentity, either at the time the field is added to the parent, or beforehand by creating a new subclass of a subentity object.
• Creating parallel history subentities, or extending an existing history object to include the fields present in the service or container subentity.
• Extending or updating existing maps to copy the data as necessary, for example between a service subentity and a history subentity.
• Updating CLFs to add new maps or other mechanisms of copying data.
• If appropriate, update the Parent field of the new subentity to be of a particular type of object.

Adding an Existing Subentity to a Parent CDO

An existing subentity can be easily added to an object by selecting its object type. On the Add a new CDO field window, select the data type Object and subsequently select the name of the existing subentity in the Field type selection list. You can then mark this field as a list and add corresponding field definitions to service related objects as required.

Additional steps may be required depending on the type of object to which you added this subentity field, like extending maps, and so forth. These steps were described previously.

In this example, you will add a subentity subclass that groups together data about contacts that you want to maintain about each of your customers. This subentity allows you to define and collect information in a subentity for each instance of Customer, and bidirectionally reference each of the Customers to its Contacts subentity.

Referencing a Named Subentity by Name

Named subentities can be referenced either by name or by index. When you have a named subentity on an object (such as a product), unique entries can be added by Name with a corresponding value.

Therefore, Designer allows you to reference the subentity either by index or the specific entry in a path selector by name instead of index.

For example, to search for the following by name:

Container.Product.Attributes("Color").Value.

You can use the following:

FindListItem (Container.Product.Attributes, Name, “Color”).Value

How to Add Fields to the ContainerDetails Subentity

Follow these steps to add fields to the ContainerDetails subentity:

1. Select the Container subclass you want to customize.
2. Click the Fields tab.
3. Select Position to CDO Definition from the Detail field’s shortcut menu to access the ContainerDetail CDO.
4. Add fields to the ContainerDetail CDO according to your business requirements.
5. If you want values to be provided for the ContainerDetail fields during the Container subclass’ Start service (usually, values for ContainerDetail fields do not need to be set until later in container processing):
a. Select the associated Start service for the Container.
b. Select Position to CDO Definition from the Details field’s shortcut menu to access the corresponding StartDetails CDO. Then add corresponding fields.
c. Add a map entry in the map StartDetails_to_ContainerDetail for the fields added to the StartDetails CDO.
Note: Refer to “How to Map a Field by Extending an Existing Map” for information on performing this procedure.
d. Configure history if desired, as follows:
1) Select the StartHistoryDetail CDO and add corresponding fields.
Note: This step is required if history record is required.
2) Add a map entry in the map ContainerDetail_to_StartHistoryDetail for the fields added to the StartHistoryDetail CDO.
Important: This step is required if history record is extended.
6. Extend ContainerTxn to update the fields if necessary:
a. Add corresponding fields to the appropriate subclass of ContainerTxn and provide CVE in the format similar to This_Value;Container.Detail.MyField.
Important: This step is required if ContainerTxn and its subclasses should be able to update those detail field values.
b. Add a map entry in the map ContainerTxn_to_ContainerDetail for the fields added to the Container Txn.
Important: This step is required if ContainerTxn and its subclasses should be able to update those detail field values.
7. Add corresponding fields to the HistorySummary CDO if history records are required.
8. Add a map entry for the fields added to the HistorySummary CDO:
a. Add a map entry in the map SummaryContainerDetailPreHistory for the fields added to the HistorySummary CDO.
Important: This step is required if you added fields for the old values to keep prehistory records.
b. Add a map entry in the map SummaryContainerDetailPostHistory for the fields added to the HistorySummary CDO.
Important: This step is required if you add fields for the new values to keep post-history records.
9. Add logic to the Start service so that if this Container type is created, the corresponding ContainerDetail subentity is also created. Refer to “Configurable Logic Flows” for specific details on:
a. Creating a user CLF
In this case, you will add your own CLF under the UserFunctions category.
b. Adding a function to your user CLF
In this case, you will add the CreateCDO function from the ObjectProcessing category. You will set the parameters exactly as shown (bold text only):
CreateOnlyIfNotExists = Transaction::__Const.BooleanTrue
Location = Container.Detail
c. Adding the user CLF to a CDO’s Events tab by overriding an existing method
In this case, you will select the Container’s associated StartDetails CDO and override the CreateContainer_User method with your user CLF.
10. Click Update DB. A dialog box appears asking you to confirm you want to save the current MDB file and update the database according to the settings in the Preferences dialog box.
11. Click Yes. A status bar appears at the bottom of the window to indicate the update is in progress. The application saves and updates the database.
Note: Refer to "Preferences Dialog Box, DB Update Tab" for information on the settings available in the Preferences dialog box. Refer to the Opcenter Execution Medical Device and Diagnostics System Administration Guide or the Opcenter Execution Core System Administration Guide for more detailed information on updating the database.

How to Add a Subentity CDO to a CDO

Follow these steps to add a subentity CDO to the Customers CDO:

1. Open Designer.
2. Click CDOs on the toolbar. The CDO Definition window appears.
3. Select Advanced from the View menu.
4. Locate the following class:

NamedDataObject>Customer

5. Select Customer. The CDO opens at the Fields tab.
6. Click Add under the Field tab. The Add a new CDO Field window appears.
7. Select the option (Create a new Subentity) from the Data Type list. The Field Type field changes to CDO Definition from which to inherit.
8. Select Subentity from the list of objects from which the new subentity inherits.
9. Name the new Customer subentity subclass CustomerContacts.
10. If desired, type a caption, for example, Customer Contacts.
11. Type a meaningful Description.
12. Select Modeling from the Storage Category list.
13. Type a Table Name for the table in which you will store your CustomerContacts data. For our example, type CustomerContacts.
14. Click Create. The CDO Field Properties window for CustomerContacts opens.
15. Verify the properties and modify if necessary.
16. Click OK. The Customer CDO now contains a field linking it to the new subentity, and the name of the field is the name of the new subentity, CustomerContacts.
17. Display the new subentity as follows:
a. Right-click on the CustomerContacts field to display the shortcut menu.
b. Select Position to CDO Definition. The new subentity is selected and its Fields tab displayed.
Note: Later, you can add fields to this new subentity to make it usable in its context as extending its parent CDO.
18. Click Update DB. A dialog box appears asking you to confirm you want to save the current MDB file and update the database according to the settings in the Preferences dialog box.
19. Click Yes. A status bar appears at the bottom of the window to indicate the update is in progress. The application saves and updates the database.
Note: Refer to "Preferences Dialog Box, DB Update Tab" for information on the settings available in the Preferences dialog box. Refer to the Opcenter Execution Medical Device and Diagnostics System Administration Guide or the Opcenter Execution Core System Administration Guide for more detailed information on updating the database.

Automated Steps

The following definitions are created:

• CustomerContacts references Customer through the Parent field.
• The CustomerContactsChanges CDO is added under SubentityChanges.
• CustomerContactsChanges references Customer through the ObjectToChange field.
• CustomerContactsChanges references CustomerContactsChanges through the ListItemToChange field.
• The CustomerContacts table has been added.

To verify, click Tables on the toolbar and use the Find button to locate the CustomerContacts table.

How to Remove a Subentity

If you remove the field in the parent CDO that owns the subentity, the subentity is not removed if there are references to it in other CDOs. To remove a subentity, you need to remove all the references to it.

Follow the steps in this example to remove the Customer Contacts subentity:

1. Select the Customer CDO.
2. Select the CustomerContacts field.
3. Click Remove below the fields area to remove the CustomerContacts field. The field is removed.
4. Select the CustomerContacts CDO.
5. Select the WhereUsed tab.
6. Double-click on CustomerContactsChanges in the list. The focus moves to the CustomerContactsChanges CDO.
7. Select the Fields tab.
8. Select the ListItemToChange field.
9. Click Clear Override. The reference to CustomerContactsChanges is removed.
10. Select the ObjectToChange field.
11. Click Clear Override. The reference to CustomerContacts is removed.
12. Select the CustomerContactsChanges CDO.
13. Click Remove below the selection tree to remove the CustomerContactsChanges CDO.
14. Select the CustomerContacts CDO.
15. Click Remove below the selection tree to remove the CustomerContacts CDO. This removes the CustomerContacts CDO and the corresponding table from the Tables definition.
16. Click Update DB. A dialog box appears asking you to confirm you want to save the current MDB file and update the database according to the settings in the Preferences dialog box.
17. Click Yes. A status bar appears at the bottom of the window to indicate the update is in progress. The application saves and updates the database.
Note: Refer to "Preferences Dialog Box, DB Update Tab" for information on the settings available in the Preferences dialog box. Refer to the Opcenter Execution Medical Device and Diagnostics System Administration Guide or the Opcenter Execution Core System Administration Guide for more detailed information on updating the database.
