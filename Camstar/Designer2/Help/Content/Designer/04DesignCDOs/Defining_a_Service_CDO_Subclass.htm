Defining a Service CDO Subclass

Service objects represent the work performed on Container objects. In Defining a Container CDO Subclass, the Start service subclass is automatically created. In Defining a NamedDataObject Subclass and Defining a RevisionedObject Subclass, a Maintenance service subclass is automatically created. Other services are available, such as inquiries and transactions. Most day-to-day tasks performed by employees are through shop floor transactions on containers.

When Defining a Service CDO Subclass

Workspace prefixes are automatically inserted before the name of an item when adding a new item, if a prefix has been assigned to the highest active workspace. Workspace prefixes indicate which workspace Designer is applying changes to. For example, the prefix "C200" would be associated to the workspace with a prefix set as "C200" in Management Studio. It is recommended you use the prefix supplied by Designer when adding new items.

You can assign or modify workspace prefixes in Management Studio. Refer to the Opcenter Execution Medical Device and Diagnostics System Administration Guide or the Opcenter Execution Core System Administration Guide for information.

Note: The base application workspace (csi) cannot have a workspace prefix assigned to it.
Task Overview

The Service class contains subclasses representing the Container transactions performed on the shop floor, such as the Start, MoveTxn, and Associate CDOs, to name a few. A step-by-step exercise follows this general discussion.

Add a Service CDO subclass

You will add your service subclass under the appropriate Siemens‑provided service CDO.

Defining a service object, for example the MoveStd transaction under ContainerTxn, uses the same procedure as used for CDOs in general. No database tables are associated with transactions, although history information is collected and stored to keep track of the transactions used on a Container, when the transactions were performed, and who performed them.

Create a ServiceDetails subentity

Some services have a ServiceDetails subentity containing information needed by the service. The simple services do not need a ServiceDetails subentity; all the information needed by the service are in the service itself. For services that have a ServiceDetails subentity, you will create a ServiceDetails subentity subclass for the new service CDO subclass. Concepts and instructions were explained in Defining a Subentity CDO Subclass and demonstrated in Exercise to Add a Subentity Through a Field.

Add fields to the service or ServiceDetails CDO subclass

For service CDOs with a ServiceDetails field, you will add the fields to the ServiceDetails subentity. For service CDOs without a ServiceDetails field (or its equivalent, like ToContainerDetails for the Split service), you will add the fields directly to the service CDO.

Override CDO references

If the new service CDO inherits a Details field, the field points to its parent CDO’s Service Details subentity, rather than to the ServiceDetails subentity belonging to the newly created service CDO. In this case, you will change the reference in the Details field of the new service CDO to point to the new ServiceDetails subentity CDO.

The new service CDO needs to point to the correct Container CDO. For services that have a ServiceDetails subentity, you will override the Container field in the subentity to point to the correct Container CDO. For services that do not have a ServiceDetails subentity, you will override the Container field in the service CDO to point to the correct Container CDO.

Add fields to the History CDO

If you extend a service by creating a subclass and adding your own fields, and if you want those new fields to be written to the service’s history records, you will add the same fields to the appropriate type of History CDO subclass and then map these additional fields from the extended service CDO to the new History CDO subclass. The three types of History CDOs for your use include:

• ServiceHistoryDetail (for services that have ServiceDetails).
• ServiceHistorySummary (for services that do not have ServiceDetails).
• StartHistoryDetail (for Start service only, in addition to ServiceHistoryDetail).

Add fields to the HistoryDetails subentity CDO

Any field that you intend to record must be copied to the HistoryDetails CDO from the service CDO. Proper recording of data will occur if you map the fields from the source CDO to its destination CDO.

First you will add a subclass to the appropriate HistoryDetails subentity, and then add the new fields to this History CDO. This will enable you to record historical information for the new Container fields every time the service is performed against the Container.

How to Add a Service CDO

The Start service and all the associated CDOs and references are automatically created when you create a subclass of the Container CDO and select Create & Configure a Start Service. Maintenance services are automatically created when you add a subclass of a NamedDataObject or a Revisioned Object CDO and select Create & Configure a Maintenance Service. For all other container services, you need to create a subclass for the needed service.

The following procedure explains how to create a subclass for the Thruput service. Follow these steps to add a service CDO:

1. Open Designer.
2. Select the Thruput service CDO from the list of classes:

Service>Update>ShopFloor>ContainerTxn>Thruput

 

3. Click Add below the CDO selection pane. The Create a New CDO Definition appears.

This window enables you to add a new subclass to this Service CDO.

4. Enter the name of this new service subclass, MyThruput in the New CDO Name field.
Important: The name of the CDO can be as many as 30 characters in length, and cannot contain spaces, illegal characters, or reserved words. Refer to “Valid Characters and Reserved Words” for information.
5. Enter a description in the Description field. The Create button is enabled if both Name and Description fields are filled.
6. Keep the default values for CDO Usage of Service Shopfloor Reversible and Storage Category of None.
Service CDOs are non-persistent and do not require storage.
7. Click Create. MyThruput is now a subclass of Thruput.
8. Select Save from the File menu. The application saves your changes.

Add a ServiceDetails CDO

To continue the example, create MyThruputDetail subentity CDO as a subclass of ThruputDetail (following the class structure of Thruput).

How to Add MyThruputDetail

Follow these steps to addMyThruputDetail subclass:

1. Select the Thruput CDO.
2. Right-click ServiceDetails field.
3. Select Position to CDO Definition to go to the ThruputDetails subentity.
4. Derive (add) the subclass, MyThruputDetail, and enter a description. Keep the other default values. The subentity is added to the class structure as follows:

Subentity>ServiceData>ServiceDetails>ThruputDetails>MyThruputDetail

5. Select Save from the File menu. The application saves your changes.

Service CDOs and their subentities do not require storage category definitions. Review how to define a Subentity CDO Subclass if necessary. You will add fields to this subentity in the next procedure.

Adding fields to the Service or ServiceDetails CDO

You can add fields to the ServiceDetails CDO (or to the Service CDO if it does not have a ServiceDetails CDO) if appropriate to your business purposes.

How to Add a Field to MyThruputDetail

Follow these steps to add field to MyThruputDetail subclass:

1. Select MyThruputDetail that you just created.

The Fields tab is displayed.

2. Click Add below the fields area.
3. Keep the data type as String. In the Name field, enter MyThruputField1.
Note: Fields names need to be unique only within the CDO.
4. Click Create.
5. Select Save from the File menu. The application saves your changes.

Creating the HistoryDetails CDO subclass

Instead of using the existing default HistoryDetails CDO for Thruput, add a new subclass to the appropriate HistoryDetails CDO, then add fields to the subclass.

How to Add MyThruputHistoryDetail

Follow these steps to add MyThruputHistoryDetail subclass:

1. Go to

 

Subentity>HistoryDetails>ServiceHistoryDetail>ThruputHistoryDetail

Note: You can also click Include inherited fields to expose them, right-click the HistoryDetail field, and select Position to CDO Definition to go to ThruputHistoryDetail.
2. With ThruputHistoryDetail selected, click Add below the selection pane. The Create a new CDO definition window appears.
3. Enter MyThruputHistoryDetail in the New CDO Name field.
4. Enter a description appropriate to your business requirements.
5. Click Create.
6. Click Update DB. A dialog box appears asking you to confirm you want to save the current MDB file and update the database according to the settings in the Preferences dialog box.
7. Click Yes. A status bar appears at the bottom of the window to indicate the update is in progress. The application saves and updates the database.

Adding fields to the HistoryDetails CDO

Add the same fields to this CDO (in this case, MyThruputField1) that you added to the Service or ServiceDetails CDO.

Note: Either add the MyThruputField1 field manually or copy it from MyThruputDetails and paste in to MyThruputHistoryDetail. If you want to copy and paste, use the CDO field shortcut menu and not the Windows keyboard shortcuts.

The next step is to map the fields, explained in Viewing Field Maps.

This completes the exercise of creating a Thruput service subclass and all related CDO configurations.
