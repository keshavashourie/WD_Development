Adding CDOs

Create or add a CDO by clicking the Add button below the selection tree or by right-clicking in the selection tree pane and selecting Add Subclass.

When Adding CDOs

Workspace prefixes are automatically inserted before the name of an item when adding a new item, if a prefix has been assigned to the highest active workspace. Workspace prefixes indicate which workspace Designer is applying changes to. For example, the prefix "C200" would be associated to the workspace with a prefix set as "C200" the highest active workspace in Management Studio. Siemens recommends you use the prefix supplied by Designer when adding new items.

You can assign or modify workspace prefixes in Management Studio. Refer to the Opcenter Execution Medical Device and Diagnostics System Administration Guide or the Opcenter Execution Core System Administration Guide for information.

Note: The base application workspace (csi) cannot have a workspace prefix assigned to it.
When Adding a Subclass

Siemens recommends using a unique name when adding a CDO subclass. If the CDO and CDO subclass share the same name, and the subclassed CDO's instances are saved in the parent CDO’s table in the database, then no instances will appear for selection during Modeling export (even when defined for both the parent and child CDOs).

If the CDO and CDO subclass have different names but are saved to the same table, all instances defined for both the parent and child CDOs are returned, regardless of whether you choose the parent or child CDO during Modeling export. The name of the subclassed CDO appears as the Object Type during a Modeling export.

Field Definitions

This table defines the fields on the Create a New CDO Definition window.

Field

Definition

New CDO Name

Unique name for the CDO. Most programming references CDOs by name.

Description

Description that enables the Create button (if entered in addition to the name).

CDO Usage

Selection determines the predefined attribute settings associated with the CDO.

Details

Button that allows you to view and enable usage attributes for the selected CDO, such as whether the CDO is a container or a named data object.

Storage Category

Reference to a table category to use for this CDO. If the category chosen is Modeling, an IsFrozen field will automatically be added to the CDO if it does not already exist. Select None if the CDO is non-persistent and does not require storage. Select Undefined if the Storage Category is to be determined later.

Create a New Table

Check box that is disabled for Container subclasses because the application’s Container table will be used. Otherwise, check this box to create a new table for the CDO subclass. In cases where a class already has a table associated with it, you most often want to use the same table for the subclass to enforce uniqueness across CDO types (for example, if you create a subclass of Product). However, if uniqueness is not a concern and you want a separate table, select Create a new Table. A message appears beside the field saying that a table is already associated with the object. The same message will appear when you click Create. Click Yes at that point to continue creating the CDO subclass.

Table Name

Unique name by which the table for this CDO is identified.

Description

Good place to document the purpose of the table.

Create & Configure a Maintenance Service

Check box that is enabled only for NamedDataObject and RevisionedObject CDOs. When you select this check box, other objects that need to be created are created and references that need to be made for this CDO to function properly are referenced for you.

Permissions

When you create a new service or compound service in Designer, you must grant access to it by assigning the access mode to the service methods.

The New method is triggered when you attempt to create a new modeling object. You must check the Create access mode for this method so the system will recognize that, for the New method, it must verify that the Create access mode is granted to a role to which the user belongs.

Roles and role memberships are managed in the Portal’s modeling objects of Role, Employee, and Organization. Refer to the Opcenter Execution Medical Device and Diagnostics Modeling User Guide or the Opcenter Execution Core Modeling User Guide for information.
