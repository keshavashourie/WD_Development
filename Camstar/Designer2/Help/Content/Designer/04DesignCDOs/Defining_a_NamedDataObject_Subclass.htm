Defining a NamedDataObject Subclass

A NamedDataObject CDO is a class of objects that is identified by a unique name. It represents static entities that do not have revisions. Named data objects have associated maintenance objects. When you add NDOs, follow the structure in the class library by relating your new CDOs to one another in the same way that the default named data objects relate to one another.

When Defining a NamedDataObject Subclass

Instances of named data objects are persistent; that is, information about them is written to the database.

Workspace prefixes are automatically inserted before the name of an item when adding a new item, if a prefix has been assigned to the highest active workspace. Workspace prefixes indicate which workspace Designer is applying changes to. For example, the prefix "C200" would be associated to the workspace with a prefix set as "C200" in Management Studio. It is recommended you use the prefix supplied by Designer when adding new items.

You can assign or modify workspace prefixes in Management Studio. Refer to the Opcenter Execution Medical Device and Diagnostics System Administration Guide or the Opcenter Execution Core System Administration Guide for information.

Note: The base application workspace (csi) cannot have a workspace prefix assigned to it.

Overview of Tasks

The overall process to define a NamedDataObject CDO is similar to that used to define a Container CDO. The only additional concepts are adding an ObjectChanges CDO and a Maintenance Service CDO for the NDO; these steps are performed automatically at the time you create the NDO when you check Create & Configure a Maintenance Service. Refer to "Automated Steps in Defining a CDO Subclass" for information.

How to Add a NamedDataObject CDO Subclass

Follow these steps to add a NamedDataObject CDO subclass:

1. Open Designer.
2. Click CDOs on the toolbar. The CDO Definition window appears.
3. Select Advanced on the View menu.
4. Expand the NamedDataObject class.
5. Select a subclass of NamedDataObject. We will use Factory for this example.
6. Click the Add button under the CDO list, or right-click on Factory and select Add Subclass. The Create a new CDO Definition window appears.
Note: The Derive from field indicates the base class for your new CDO.
7. Enter the name MyFactory in the New CDO Name field.
Important: The name of the CDO can be up to 30 characters in length, and cannot contain spaces, illegal characters, or reserved words. Refer to "Valid Characters and Reserved Words" for information.
8. Enter a Description.
Note: The Create button is not enabled until both the New CDO Name and Description fields are filled.
9. Keep the default values for CDO Usage and Storage Category.
10. Do not select Create a New Table.
Note: The Factory object already has a table associated with it. Refer to "When to Create a Table" for information.
11. Ensure Create & Configure a Maintenance Service is selected.
12. Click Create. The new NDO, MyFactory, appears in the selection tree and MyFactory is selected.

The CDOs required for maintenance and the associated required field overrides are also automatically created for this NDO.

a. Select MyFactory’s General tab, if not displayed.
Important: Take care not to change the value in the Abstract field. Note that the Caption picked up the CDO name but put spaces after each capital (uppercase) letter.
b. Modify Caption according to your business needs.
13. Select Save from the File menu. The application saves your changes.

Automated steps

The following associated CDOs were automatically defined:

• MyFactoryMaint is added under Service>Maintenance>NamedDataObjectMaint>FactoryMaint
• MyFactoryMaint references MyFactoryChanges through the ObjectChanges field.
• MyFactoryMaint references MyFactory through the ObjectListInquiry field.
• MyFactoryMaint references MyFactory through the ObjectToChange and ObjectListInquiry fields.
• MyFactoryChanges is added under NamedDataObjectChanges>FactoryChanges.
• MyFactoryChanges references MyFactory through the ObjectToChange field.

Refer to "Automated Steps in Defining a CDO Subclass" for information.

How to Add Fields to the User-Defined NDO

In this exercise, you will add two fields: a string type and an object type. On the user interface, both fields will be optional (user entries will not be required). Refer to "CDO Fields" for information.

Follow these steps to add fields to the User-Defined NDO subclass:

1. Select the CDO you just defined previously. In this case, it is MyFactory.
2. Select the Fields tab.
3. Click Add on the Fields tab (or right-click on the pane and select Add field) to add a field.
4. Configure the new field as follows:
a. Select Stringas the Data Type.
b. Select [String] as the Field type.
c. Enter Parm1 for the field name.
Note: Field names must not contain spaces, illegal characters, or reserved words. Refer to "Valid Characters and Reserved Words" for information.
d. Enter Parameter 1 for the Caption.
Note: This value will appear as the field’s caption if using Portal Studio, Modeler, or Visual Controls. Captions can have spaces for easy reading.
e. Enter a description.
f. Keep Add Field to Associated Service Objects selected. This adds the field to MyFactoryChanges CDO.
g. Click Create. The CDO Field Properties window opens at the Options tab.
h. Under Accessibility, click Read/Write.
i. Keep the other default values.
j. Click OK.
5. Click Add to add a second field.
6. Configure the second field as follows:
a. Select Object from the Data Type list.
b. Select Owner as the Field type and keep the field name, Owner.
c. Optionally, change the description to fit your business requirements, or keep the default.
d. Click Create. A CDO Field Properties window opens at the Options tab.
Note: In the General tab, the column name for this field is denoted as OwnerID.
e. Click OK.
7. Click Update DB. A dialog box appears asking you to confirm you want to save the current MDB file and update the database according to the settings in the Preferences dialog box.
8. Click Yes. A status bar appears at the bottom of the window to indicate the update is in progress. The application saves and updates the database.
Note: Refer to "Preferences Dialog Box, DB Update Tab" for information on the settings available in the Preferences dialog box. Refer to the Opcenter Execution Medical Device and Diagnostics System Administration Guide or the Opcenter Execution Core System Administration Guide for more detailed information on updating the database.

This completes the exercise of creating a NamedDataObject.

How to Remove an NDO

If you need to delete the NDO subclass that you created, you must remove their associations with other CDOs in the reverse order that the associations were created. In the following example, we will remove MyFactory.

Follow these steps to remove an NDO subclass:

1. Open Designer.
2. Click CDOs on the toolbar. The CDO Definition window appears.
3. Select Advanced from the View menu.
4. Select the Changes object (in this example, MyFactoryChanges) and clear the override for the field ObjectToChange.
5. Select the maintenance object (in this example, MyFactoryMaint) and clear the override for the field ObjectChanges.
6. Remove the changes CDO (in this example, MyFactoryChanges).
7. Remove the NDO Maintenance CDO (in this example, MyFactoryMaint).
8. Remove MyFactory.
9. Click Update DB. A dialog box appears asking you to confirm you want to save the current MDB file and update the database according to the settings in the Preferences dialog box.
10. Click Yes. A status bar appears at the bottom of the window to indicate the update is in progress. The application saves and updates the database.
Note: Refer to "Preferences Dialog Box, DB Update Tab" for information on the settings available in the Preferences dialog box. Refer to the Opcenter Execution Medical Device and Diagnostics System Administration Guide or the Opcenter Execution Core System Administration Guide for more detailed information on updating the database.
