Defining a RevisionedObject Subclass

There are specific steps that are required when creating a RevisionedObject CDO. When creating the RO, you can select the option to automatically create the required associated CDOs and required fields.

The overall steps to define a RevisionedObject are similar to those used to define a NamedDataObject CDO. The only additional steps address adding a RevisionBase CDO and changing the CDO associations for the RevisionedObject and the RevisionBase CDOs, which are performed automatically if you select the check box on the Create a new CDO Definition window to Create a Maintenance Service.

The RevisionBase CDO

RevisionBase is a named data object for providing the ROR (revision of record) and revisions. The ROR attribute provides the ID of the current revision of record. The Revisions attribute provides a list of revision instances associated with the revisioned object. For each RevisionBase, there is at least one RevisionedObject.

Automatically Generated Associated CDOs

When you add a RevisionedObject (RO), if you select the check box to Create & Configure a Maintenance Service, the actions listed immediately below are performed automatically:

• Add a RevisionedObjectChanges CDO

The purpose of adding an ObjectChanges CDO is to provide a scratch area to hold changes before committing them to the RevisionedObject. The ObjectChanges CDO is exposed to the Client. This means that if changes are made to the ObjectChanges CDO, the changes are validated first before they are written to the RevisionedObject. This feature provides a layer of protection from accidental changes. The validated changes to the RevisionedObject are in turn written to the database.

• Add a RevisionBase CDO (actually a NamedDataObject CDO)

The purpose of adding a RevisionBase CDO is to contain the common things associated with all the revisions for this object, such as the name, the list of IDs, and the revision of record.

• Link the RevisionedObject (RO) and the ObjectChanges CDO

Overriding field properties within a CDO is a method of linking two CDOs together. Inherited fields inherit the field properties from the superclass from which the CDO is derived. The process of overriding a field is changing a field property of an inherited field for the specified CDO. Linking objects together through a field is the process of changing the field type to be the name of the CDO to which it is being linked. This causes the field within one CDO to point to another CDO. Here you are linking the ObjectChanges CDO to the RevisionedObject CDO.

• Add a maintenance CDO to maintain the RevisionedObject

The purpose of adding a Maintenance CDO is to maintain the RevisionedObject CDO.

• Reference the new RevisionedObject in the Maintenance CDO

The purpose is the same as for creating an override in the ObjectChanges CDO except here you are linking the Maintenance CDO to the RevisionedObject, ObjectChanges, and the RevisionBase CDOs.

• Change the CDO associations for RevisionedObject and RevisionBase CDO

The purpose of changing the CDO associations is to link the RevisionedObject CDO to the RevisionBase CDO.
