Defining Employees

An Employee is a user who performs activities in the application such as maintaining modeling definitions, making inquiries, managing security administration, and performing shop floor transactions. A system administrator uses security administration features to grant privileges to employees so they can access those activities.

Each employee must have a valid login account, and the employee name must match the login account ID. Contact your system administrator for the exact syntax of user names.

Employees can be defined without accounts, but those employees cannot log in. They can be entered as the employee who performed a container or resource transaction. For example, a supervisor with a valid login account (and the appropriate permission) can log in to the application and access the Start page. The employee name recorded on the Start page can be the supervisor or another employee, whoever actually performed the work of starting the container. This employee may or may not have an account.

Session values can be set for each employee to limit the view of someone who is performing transactions. The employee sees only what he or she is supposed to see, and has a shorter list of values to search from. This limits searching time and presents fewer opportunities for mistakes.

Security Model

The security model for the application is based on a role-based access control model. The system administrator assigns role memberships to an employee to control the employee’s access to all or parts of the application. When you specify a primary organization and role memberships for an employee, you are setting up the security rights for that employee. To perform any action, a user must have a role in an organization, either directly or indirectly through role propagation.

Roles are defined on the Role page. You can assign role memberships on the Employee page or on the Role page. However, you can only assign permissions for that role on the Role page.

The Opcenter Execution Core Security Guide includes a chapter on security administration. It discusses permission types and modes, how the authentication and authorization process works, and how user permissions are validated.

Default Employees

The application provides the following employee definitions by default:

• Administrator
• CamstarAdmin
• InSiteAdmin
• System

Use one of these employee names when initially logging on to the application.

The default Portal menu is assigned to the Administrator, CamstarAdmin, InSiteAdmin, and System employees automatically in an initial implementation of Opcenter Execution Core or when converting or updating to a new version and upgrading default instance data. Use the Portal Menu Definition field on the Employee page to assign Portal menus to other employees.

Default Roles

Siemens also provides several predefined roles for the default Corporate organization. The default employees are assigned membership in all or some of the default roles. Additional default roles are provided to users who have licensed Change Management.

When Defining an Employee

At least one of the default employees must be a valid Active Directory user to be able to log into the Portal for the first time.

If you are defining employees for the first time, be sure to create the employee definition for yourself as administrator. Use your Windows login name as your employee name. If you are creating a definition for another employee, use that employee’s Windows login name.

Employee definitions in the application are used as follows:

• As the logged-in employee to the Portal, the Organization defaults to your primary organization. Only the organizations in which you have a direct role or a role through propagation will be available for selection on the Portal pages.
• When performing a record search in the application, you can enter owner as part of the search criteria. The owner is the employee associated with the quality records to be searched.

Note the following:

• Employee contains these optional modeling definitions: Organization, Dictionary, ESig Role Group, Factory, Training Plan, Operation, and Work Center.
• Employee is an optional field in all container transactions and in all resource transactions.

When Defining Escalation Recipients

An escalation recipient is the person who will receive an e-mail notification when an employee has upcoming, due, or overdue work. For example, you can send an e-mail notification to an employee's manager if work is due. You define escalation recipients using the Employee field in the Escalation Recipients grid.

The Change Mgt Settings modeling object enables you to set up reminder notifications to be sent to escalation recipients when an approver or collaborator has an incomplete task. The application sends the reminder to the escalation recipient specified for the employee if you select this type of reminder notification. Refer to the Opcenter Execution Core Modeling User Guide for information.

The application will not send e-mail notifications if you do not select escalation recipients in the Escalation Recipients grid. Ensure that the E-mail Address field is complete in each escalation recipient's Employee modeling object instance or the recipients will not receive the e-mail notifications.

How to Define an Employee

Follow these steps to define an Employee:

1. Open the Employee page. The Employee page appears within the Modeling page.
2. Click New. Blank fields appear for you to define a new instance.
3. Enter the name of the employee in the Employee field.
4. Enter the access level for the employee in the Access Level field.
5. Enter optional information according to your business requirements. Refer to the field definitions table for information on the optional fields.
6. Click Save. The application saves the modeling object and displays a success message.
