Defining Operations

An Operation is a manufacturing or processing point where inventory and production activities are tracked. The Operation definition describes items such as the reason codes, processing rules, and the allowed transactions for the movement of material through the Operation. In contrast, specifications define the processing that is performed at an Operation.

Some examples of Operation information include:

• References to user codes for recording of loss, bonus, rework, and shipping information
• Optional designation of the Operation as an inventory, in transit, or outside service point
• Designation of allowed and disallowed transactions
• Indication if the in-queue status is used, therefore requiring a Move In

You can specify an Operation when creating an event to identify the manufacturing or processing point where the event was detected.

Types of Operations

Semiconductor Shop Floor provides different types of Operations that each correspond to a specific transaction: Scheduled Operations, WIP Operations, In-Transit Operations, and Inventory Operations. The following table describes the Operation types:

Operation Type

Description

Scheduled Operation

Scheduled Operations are required to track the inventory and production activities for scheduled specs. Each Scheduled Operation corresponds to the Scheduled Spec according to the shop floor operation that it tracks. For example, the Assembly Scheduled Operation corresponds to the Assembly Scheduled Spec. If your workflow references a Scheduled Operation through a Scheduled Spec, you must execute a lot schedule release to move the lot into WIP.

The application provides the following Scheduled Operations:

• Assembly Scheduled Operation
• Back Grind Scheduled Operation
• Test Scheduled Operation
• Wafer Scheduled Operation
• Wafer Sort Scheduled Operation

WIP Operation

WIP Operations are required to track the inventory and production activities for WIP Specs, which in turn define WIP steps. Each WIP Operation corresponds to the WIP Spec according to the shop floor operation that it tracks. For example, the assembly WIP Operation corresponds to the assembly WIP spec.

Semiconductor Shop Floor provides the following WIP Operation:

• Assembly WIP Operation
• Back Grind WIP Operation
• Test WIP Operation
• Wafer Sort WIP Operation
• Wafer WIP Operation

In-Transit Operation

In-Transit Operations are required to track the inventory and production activities for In-Transit Specs. Each In-Transit Operation corresponds to the In-Transit Spec according to the shop floor operation that it tracks. For example, the Die Bank In-Transit Operation corresponds to the Die Bank In-Transit Spec. Semiconductor Shop Floor provides the following In-Transit Operations:

• Die Bank In-Transit Operation
• Test store In-Transit Operation
• Wafer In-Transit Operation
• Wafer Sort In-Transit Operation

Inventory Operation

Inventory Operations are required to track the inventory and production activities for Inventory Specs, which begin and end workflows. Each Inventory Operation corresponds to the Inventory Spec according to the shop floor operation that it tracks. For example, the Die Bank Inventory Operation corresponds to the Die Bank Inventory Spec. Semiconductor Shop Floor provides the following Inventory Operations:

• Die Bank Inventory Operation
• Test Store Inventory Operation
• Wafer Inventory Operation
• Wafer Sort Inventory Operation

You can use the application-provided user code group, Qty Adjust Reason Group, or create a new group to accommodate operation-specific quantity adjust reasons.

Buy Reason

Name of the user code group that defines buy reasons for the Operation. A buy is an increase to the quantity of a container, typically attributed to an accounting entity, such as the engineering department.

Default Rollup Reason

Name of the user code group that defines rollup reasons for the Operation. Container quantity changes are recorded at the lowest level (child) container and can use more than one reason code. The quantities are then rolled-up to intermediate and top-level parent containers. When the rollup occurs, only one reason code is applied to the parent containers. The application uses the rollup reason referenced in the Operation, unless overridden by the user during the quantity transaction.

You can use the application-provided user code group, rollup reason group, or create a new group to accommodate Operation-specific rollup reasons.

Name of the user code group that defines component defect reasons for the Operation. A component defect refers to a defective BOM component that is not counted as a loss against the quantity of the associated container.

How to Define an Operation

Follow these steps to define an Operation:

1. Select Main from the Modeling menu. The application displays the Modeling page.
2. Click type Operation. Where type is the Operation type (example, Assembly Scheduled Operation). The application displays the selected Operation page within the Modeling page.
3. Click New. Blank fields appear for you to define a new instance.
4. Type a name for the Operation in the type Operation field. Where type is the Operation type (example, Assembly Scheduled Operation).
5. Enter a Thruput Reporting Level.
6. Enter optional information according to your business requirements. Refer to the field definitions table for information on the optional fields.
7. Click Save. The application saves the modeling object and displays a success message.

How to Specify a Transaction that Is Disallowed for This Operation

Follow these steps to specify a transaction that is disallowed for this Operation:

1. Perform the "How to Define an Operation" procedure.

Or

Select an existing Operation instance.

2. Expand the Details section.
3. Click Add new row on the Disallowed Transactions grid. The application adds a blank row to the grid.
4. Select a transaction for entry in the Txn Type field.
5. Repeat steps 3-4 as needed to add another disallowed transaction.
6. Click Save. The application saves the modeling object and displays a success message.
